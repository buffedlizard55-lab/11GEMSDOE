EXECUTIVE SUMMARY

What this file is, and how to submit it without losing a slot.

The DOE GEMS Prize Challenge asks for a single-band float32 GeoTIFF of predicted fault presence on the training raster's own grid. This page has the file, the exact note text, and the six steps. Everything else on this site is the evidence behind the file.

The six steps, in order

  1. Download the file above. One click, no login, no manual step. If you prefer to rebuild it yourself: bash scripts/download_competition_data.sh --with-aux, then python scripts/prepare_data.py, then python scripts/build_submission.py --arm structural --area-fraction 0.06.
  2. Check it before you upload. python scripts/validate_submission.py data/gems-structural-area06-v1.tif. It re-opens the written file and asserts the CRS, geotransform, shape, band count, dtype, value range, nodata and the null-outside-bounds rule. It exits non-zero if anything fails. Do this every time — a rejected upload costs a weekly slot.
  3. Open the DrivenData submission form for competition 306 and choose the .tif under File to submit. The form accepts "a single-band GeoTIFF (.tif) file, or a .zip file containing a single GeoTIFF … It must match the submission format's CRS, shape, and geotransform." A single .tif is simpler; do not zip it unless you have a reason to.
  4. Paste the note from the green box above into Note (optional). The form's own example is "clustering with k=25" — the point is to tell your own submissions apart later. Use the text verbatim so the ledger and the file agree.
  5. Record the receipt. Write the submission ID, the UTC timestamp, the file SHA-256 above, and the public score into docs/submission_ledger_template.csv. The team has lost the file-to-score link once already; that is how we ended up unable to say which file produced 0.1563.
  6. Read the public score, then stop. The public leaderboard is the public split only. The Initial Prize Round scores a private set, and the Final Round re-scores against a label set expanded by expert review of every team's submission. Do not re-upload in a hurry to chase a public number.

Why your earlier upload was rejected with “Predicted values must be in range [0, 1]”

That message comes from the platform reading the band and finding at least one pixel outside the unit interval. In our experience the causes, most frequent first, are:

  1. A nodata sentinel written as a real number. Writing -9999 or -3.4e38 into a float32 band means the platform reads it as data. The official page requires "data outside the bounds is null or nan" — NaN, not a number. This is the single most common cause.
  2. Unclipped model output. Logits, counts, or a score that was never squashed into a probability. Our pipeline clips to [0, 1] as a construction step, not as a post-hoc patch.
  3. float64 or an integer band. The page requires "datatype of 32-bit float (float32)". A float64 band promoted at write time still trips the check on some paths.
  4. A multi-band stack. The page requires "a single layer". A 19-band feature stack is not a submission.

Our file reports min 0.0, max 1.0, out-of-range pixels 0, NaN outside the bounds in the validation report, and python scripts/validate_submission.py re-derives all of it from the file on disk. It also has a regression test that deliberately writes an out-of-range file and asserts the validator refuses it.

What is in the file, and what it is not

Model
Histogram gradient-boosted pixel classifier (scikit-learn), CPU only, no GPU required.
Inputs
The 19 official GeoDAWN feature bands, plus a 9-band topographic stack and a 7-band airborne-gamma radiometric stack built from public USGS 3DEP and GeoDAWN data (GeoDAWN is CC0 1.0).
Derived channels
Nine: structure-tensor coherence of the horizontal gradient of the RTP magnetic anomaly and of the isostatic gravity anomaly at 300 m and 800 m, coherence of the supplied TMI horizontal-gradient band, the Laplacian of the basement surface, its gradient coherence, its 500 m relief, and the coherence of the surface-conductivity gradient.
Emission
Top 6% of in-footprint pixels by probability, as a binary mask, corridor width 0 px, plus the supplied catalogue at 1.0. The 6% is the measured optimum of a four-fold leakage-free spatial holdout; the response is 0.0943 at 40% area, 0.1324 at 6%.
Holdout score
0.1366 mean over four spatially held-out folds, official metric, official mask. The paired control was 0.1324 — a +0.004 difference with a paired t of 1.3 on four folds. Not statistically significant.
What it is not
Not a discovery. Not a proven leaderboard gain. A holdout score on held-out mapped faults is a proxy for the private set, which the organisers say is made of faults an expert judged to be missing from the map.

Read this before you publish it anywhere. This is an open competition with a public leaderboard. A public download hands the identical artefact to every other entrant. We publish it because a validated, reproducible artefact is the deliverable this repository exists to produce, and because the provenance and hashes being visible is worth more than the secrecy. That is a judgement call, not a neutral one, and it is yours to reverse for your own team.

Why 0.1563 kept coming back

Two separate mechanisms, both measured, neither a coincidence of rounding:

  1. GEMSDOE1 and 5GEMSDOE published the same file. SHA-256 7f00890a…, 570,890 bytes, identical pixels, three separate repositories. Confirmed by fetching and hashing all three.
  2. Everything else was tuned against a shortcut the contest removes. 8GEMSDOE shows the same 0.1563 from a different raster, and the public leaderboard shows unrelated competitors at 0.1563 too. Our detector families were all selected against the mapped catalogue. The organiser confirmed on 2026-09-16 that known USGS/INGENIOUS fault pixels "are masked / excluded from evaluation, so they do not count towards penalty terms" — so reproducing the catalogue is worth nothing on the real metric. Re-scored on a leakage-free holdout, our historical files look strong (0.18–0.45) and still score 0.1563 in the contest, because they were fitted on the very traces being held out. That gap is the actual finding, and it is larger than any model variant we tested.

Full re-scoring: diagnosis.json. File identity: the audit.

What we learned that changes the target

“New fault” includes newly mapped geometry of an existing system

"For the purposes of this competition, 'new fault' means 'any fault pixel not already captured by USGS/INGENIOUS and can include newly mapped geometry of an existing fault system." — chrisk-dd, DrivenData Staff, 2026-09-22. The unmapped continuation of a mapped fault is in scope, which is why hypothesis H4 exists. It did not win, and we say so.

The organisers will not say what the labels are made of

"We're not sharing details about the data sources, fault types, or coverage behind the test faults beyond what's in the problem description." — 2026-09-24. So any claim that this model or that one "uses what the experts used" is a guess. We do not make one.
