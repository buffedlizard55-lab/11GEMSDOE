Submission file requirements

The official problem description requires a single-band, 32-bit float GeoTIFF, on the training raster's EPSG:32611 grid at 100 m resolution and same bounds. Prediction values must be in [0, 1]; data outside the bounds must be null/NaN. Match the sample submission's exact transform and valid-data mask before uploading.

These are format checks, not a guarantee of scientific quality or leaderboard score. See the official submission specification.

How to make a competition submission

  1. Obtain the official files. Enroll/access the competition data tab and place data privately under data/. Inputs needed include the training features, raster/vector fault labels, sample template, and (if used) the supplied DEM-links CSV.
  2. Run the experiment first. Use fixed geographic blocks and the official distance-weighted Tversky metric. Keep all folds/metadata in the results record. An experiment must beat the current holdout best before it is considered for a submission slot.
  3. Build a candidate GeoTIFF. Preserve the sample grid exactly. Write a single float32 prediction band with finite in-range predictions and correct nodata/masking.
  4. Audit it locally. Install Rasterio in the analysis environment and run python scripts/audit_submissions.py path/to/candidate.tif --template path/to/sample_submission.tif. For old submissions, pass all files or their parent directory to detect duplicates.
  5. Give it a unique name and note. Use a method-specific version, e.g. gems_h1_strain_orientation_v1.tif. The DrivenData note should explain the main strategy and version, not promise a score.
  6. Upload only after gates pass. On the official contest submission form, choose the validated TIFF and enter the unique note. Keep the submission ID, uploaded file SHA-256, model/config/data hashes, and public score in a ledger.

We cannot provide a real file or submission note for a candidate until it is trained, validated, and exported from the official grid. The steps above are instructions, not a statement that a model is ready.

Why 0.1563 repeated?

The public primary TIFF archived by GEMSDOE and by 5GEMSDOE is byte-for-byte the same: 570,890 bytes, SHA-256 7f00890a62878d612fb5eef67a9a364a2df819433dde74b6762ce4fc0fc4fe15, with matching georeferenced pixels. The team's 5G anchor record links this artifact to score 0.1563, consistent with the official leaderboard row. This is confirmed artifact reuse—not merely rounded-score coincidence. The actual upload receipt is not public in this workspace, so the platform-side uploaded bytes are not independently verified.

The 8G site also reports 0.1563, but its published TIFF has different bytes and different same-grid pixel values from the shared file. This confirms that an equal displayed score can arise from distinct predictions too. Run python scripts/audit_submissions.py path/to/old/submissions/ for any additional files. A matching score without matching pixel comparison must remain “same displayed score; identity not established.”
